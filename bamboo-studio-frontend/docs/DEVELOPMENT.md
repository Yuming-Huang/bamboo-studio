# 开发交接

## 当前边界

本次拆仓保留当前 0.8.0 功能，集中处理源文件归属、相对路径、可构建性和交接说明。前端几何与后端计算几何仍各有实现；没有趁拆仓重写为共享几何包。变更时应保持二者一致。

前端承载交互、预览、应力着色、方案草稿与文件导出。后端承载输入检查、候选生成、Karamba3D 求解及结果序列化。两者通过 `bamboo-local/v1` 请求和 `bamboo-local-result/v1` 结果通信。

## 修改入口

| 目标 | 前端 | 后端 |
|---|---|---|
| 修改阶段名称或按钮 | `ui/app.js`、`ui/workflow-guide.mjs` | 通常无须修改 |
| 调整屋面颜色、透明度 | `ui/roof-style.mjs`、`ui/renderer.js` | 外观变化不触发重算 |
| 增加可编辑参数 | `ui/core.js` 默认值、控件、编辑器与导出 | `Input.cs` 白名单、`Solver.cs` 映射及 Pack |
| 修改几何 | `ui/core.js` 和导出几何 | `Kernel.cs`，并同步 GH 源码 |
| 扩展搜索维度 | `ui/search-space.mjs` 与设置界面 | CandidateSpace/ComparisonEngine 对应代码及预算检查 |
| 修改阈值 | `ui/screening.mjs` 展示 | `Input.cs` 与计算核心的实际判定 |
| 修改联机协议 | `ui/client.mjs`、`desktop/KarambaClient.cs` | `LoopbackServer.cs`、`Jobs.cs` |

## 增加构型

1. 分配稳定的新 type ID，保留现有 ID。当前集合是 0、1、2、4、5，不等于固定可扩展上限。
2. 定义参数、单位、默认值和适用范围，明确哪些属于共有条件，哪些只适用于这一构型。
3. 同步后端参数白名单、几何构建、节点连接、支承与构件角色。扩展 `Solver.cs` 中的类型集合及结果映射，更新 CandidateSpace 和比较策略。
4. 前端增加图标、可选项、参数编辑器和对应几何；更新搜索计数、草稿恢复及导出路径。界面文案继续使用“各构型”或“候选构型”。
5. 同步 GH 相应组件。GH 的独立聚合源码与插件 Kernel 是不同载体，修改一份不会自动更新另一份。
6. 验证同参数下预览、实体显示、导出和计算模型一致，再做 Karamba3D 实际求解与 GH 对照。包含失败、超限、无推荐、用户坚持选非推荐方案等路径。

## 状态与兼容性约束

- “求解完成”与“初筛通过”分开显示。无可行结果时仍可能有已求解的参考数值；没有求解时数值为 null。
- 用户选定的构型在编辑时持续保留；参数变化使计算过期，不应把几何退回未选型原型。
- 修改前基准与当前修改保存完整各自参数，不能共用可变对象。
- 前后应力图使用一致色标；选择进入屋面的对象必须与导出参数一致。
- 未通过初筛也可进入屋面阶段，但不得移除对应状态。屋面仅改变外观。
- 榀距由用户确定，当前优化不自动改变。
- 保留原草稿和演示预设迁移键，避免因更名反复覆盖用户数据。
- 不在生产模式启用测试回放，不在 Karamba3D 故障时使用假结果或其他求解器冒充。

## 验证层次

前端 `npm test` 验证状态流转与数据处理；桌面回放验证真实 WebView2 加载和渲染。后端 Search 测试使用模拟评分，Adapter 测试使用未求解记录；它们验证软件契约。GH 组件编译检查验证 C# 编译，不验证 GH 画布连线和许可状态。

正式数值验收需在 Rhino 中实际调用 Karamba3D，并记录输入、插件版本、Karamba 版本、各构型结果和 GH 对照条件。本次拆仓没有运行新的真实结构计算。

## 发布

前端执行 `Build.ps1`，分发整个 `artifacts/desktop`。后端执行 `Build.ps1`，分发自己的 `.rhp`。界面资源嵌入 DLL，修改 UI 后需要重新发布桌面程序；只有后端代码改动才需要替换插件。不要为了文案修改让用户反复安装 Rhino 插件。

部署替换文件前由使用者保存方案并关闭占用文件的程序。拆仓与上传本身不执行部署替换。
